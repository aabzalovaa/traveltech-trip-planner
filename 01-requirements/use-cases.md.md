### UC-001. Отслеживание статуса рейса

**Название:** Отслеживание статуса рейса
**Акторы:** 
*Система
*Провайдер статусов рейсов
*Резервный провайдер статусов

**Предусловие:** 
У пользователя есть оформленная и оплаченная поездка с активным авиарейсом.

**Основной сценарий:**
1. Система по расписанию запрашивает у провайдера статус рейса.
2. Система проверяет актуальность данных (не пришли ли они с большой задержкой).
3. Система фиксирует новый статус рейса:
   * Если статус «Без изменений» — сценарий завершается.
   * Если статус «Задержан» или «Отменен» — переходим к шагу 4.
4. Система обновляет общий план поездки (помечает связанные события как «Требующие внимания»).
5. Система инициирует отправку уведомления пользователям (переход к UC-002).

**Альтернативный сценарий:**
* **А1. Данные пришли с задержкой (шаг 2):**
  2а. Система видит, что данные обновились слишком поздно.
  2б. Система не отправляет пользователю уведомление сразу, а запрашивает подтверждение статуса у альтернативного источника (например, через API авиакомпании).
  2в. Если статус подтвердился — система фиксирует изменение и переходит к основному сценарию. Если нет — игнорируем событие.

**Исключения:**
* **E1. Провайдер статусов не отвечает:** система повторяет запрос, затем ждёт следующего цикла опроса. Событие не публикуется, пользователь видит последний сохранённый статус.

### UC-002. Получение уведомления об изменении рейса

**Название:** Получение уведомления об изменении рейса
**Акторы:** 
* Система
* Сервис доставки push
* Участник / Организатор

**Предусловие:**
* У пользователя есть актуальный рейс.
* Обновилась информация о рейсе (после выполнения UC-001).

**Основной сценарий:**
1. Система определяет получателей: всех участников поездки.
2. Система формирует текст уведомления (например, «Рейс отменен. Мы подобрали для вас альтернативы»).
3. Система сохраняет уведомление в «Центр уведомлений».
4. Система отправляет Push-уведомление через сервис доставки.
5. Пользователь получает Push-уведомление на экран телефона.

**Альтернативный сценарий:**
* **А1. Пользователь оффлайн (шаг 4):**
  4а. Сервис доставки сам хранит Push.
  4б. Когда пользователь выходит в сеть, сервис доставки присылает отложенный Push на экран телефона.
  4в. Если пользователь смахнул Push или пропустил его, при входе в приложение он видит уведомление в «Центре уведомлений». После показа уведомление помечается прочитанным.

### UC-003. Просмотр и выбор альтернативных вариантов рейса

**Название:** Просмотр и выбор альтернативных вариантов рейса
**Акторы:** 
Организатор / Участник (только Организатор может выбирать и изменять бронирования).

**Предусловие:**
* Система зафиксировала изменение статуса.
* Пользователь получил уведомление и открыл приложение, чтобы посмотреть варианты.

**Основной сценарий:**
1. Система определяет, какой рейс изменился, и запрашивает варианты замены через сервис бронирования.
2. Система фильтрует полученный список по правилам:
   * хватает ли времени на пересадку (с учетом часовых поясов)
   * подходит ли тариф по багажу
   * нужна ли виза
3. Система формирует список и показывает пользователям до трех альтернативных варианта.
4. Организатор просматривает предложенные варианты.
5. Организатор выбирает подходящий вариант.
6. Система проверяет его роль и запрашивает перебронирование.
7. Система обновляет общий план поездки с учетом нового выбора.
8. Система уведомляет остальных участников об изменении плана.

**Альтернативный сценарий 1 (Вариант просматривает Участник поездки на шаге 4):**
4а. Участник заходит на экран с альтернативами.
4б. Участник может просматривать предложенные варианты, но кнопка «Выбрать» для него недоступна.
4в. Система показывает подсказку: «Только Организатор поездки может изменять бронирования».

# TravelTech: как работает система

## Коротко

Система следит за рейсами в поездке. Если рейс отменили или задержали, она сообщает всем участникам, находит замену и после выбора Организатора обновляет общий план.

## Кто пользуется

- **Организатор** смотрит план, выбирает или отклоняет замену, добавляет участников.
- **Участник** только смотрит план, варианты и уведомления.

## Из чего состоит система

| Блок | Что делает |
|---|---|
| Mobile App, Web App | Интерфейс. В мобильном приложении план доступен оффлайн |
| API Gateway | Входная дверь: проверяет, что пользователь вошёл и состоит в поездке |
| Core Trip Service | Хранит план, участников, рейсы и брони. Считает запас времени на пересадку. Обновляет план после смены рейса |
| Monitoring Service | Следит за статусами рейсов и сообщает о сбоях |
| Alternatives Service | Подбирает замену, принимает выбор Организатора и бронирует |
| Notification Service | Отправляет push и хранит уведомления в «Центре уведомлений» |
| Kafka | «Почта» между сервисами |

У каждого сервиса своя база данных.

**Внешние системы:** банковская платформа (вход и гражданство), Booking System (уже существующая система бронирования и оплаты), Flight Status API и резервный источник статусов, Visa API, Push Provider.

## Как это работает

1. **Рейс ставится на слежение.** Core Trip берёт подтверждённые брони из Booking System и сообщает Monitoring, за какими рейсами следить.
2. **Monitoring следит.** Он регулярно спрашивает статус рейса. Если данные пришли с большой задержкой, он перепроверяет их у резервного источника. Повторные сообщения игнорирует. Если источник не отвечает, это не считается отменой: он просто повторит запрос позже.
3. **Происходит сбой.** Рейс отменён или задержан сильнее допустимого. Monitoring сообщает об этом через Kafka.
4. **Три сервиса реагируют одновременно:**
   - Core Trip обновляет статус рейса и помечает зависимые элементы (трансфер, отель, активность) как «Требуют внимания»;
   - Notification отправляет push всем участникам;
   - Alternatives подбирает замену.
5. **Пользователь открывает приложение.** Он видит уведомление и варианты замены. Если push не дошёл, уведомление всё равно лежит в «Центре уведомлений», и пользователь получит его при входе.
6. **Организатор выбирает вариант.** Alternatives проверяет, что это Организатор, и что вариант ещё актуален, затем бронирует его в Booking System. Повторный клик не создаст вторую бронь. Участник может смотреть варианты, но выбрать не может.
7. **План обновляется.** Alternatives сообщает, что замена забронирована. Core Trip обновляет рейс и брони в плане и сообщает Monitoring: старый рейс убрать, новый поставить на слежение. Остальные участники получают уведомление.
8. **Просмотр плана.** Рядом с рейсом показывается время последней проверки и пометка, если данные устарели.

### Что считается сбоем

Если после рейса есть пересадка, считаем запас: время между прилётом и вылетом следующего рейса минус 60 минут на саму пересадку. Задержка больше запаса считается сбоем, но порог не больше 30 минут. Без пересадки порог 30 минут. Если пересадка не держится, замену ищем для следующего рейса.

### Как проверяются варианты замены

- **Пересадка:** хватает ли времени с учётом часовых поясов аэропортов.
- **Багаж:** сравниваем условия с текущей бронью и показываем различия.
- **Виза:** гражданство берём из банковской платформы, правила из Visa API. Если проверить нельзя, вариант помечается «визу нужно проверить самостоятельно».

## События в Kafka

| Топик | Кто пишет | Кто читает | О чём |
|---|---|---|---|
| `trip.disruption` | Monitoring | Core Trip, Alternatives, Notification | Рейс сломался |
| `alternative.booked` | Alternatives | Core Trip, Notification | Замена забронирована |
| `flight-tracking.updated` | Core Trip | Monitoring | За каким рейсом следить |

## Где хранятся данные

| БД | Что внутри |
|---|---|
| Trip DB | Поездки, участники, элементы маршрута, рейсы, брони |
| Monitoring DB | Рейсы под слежением, источники данных, история статусов |
| Alternatives DB | Варианты замены, операции выбора |
| Notification DB | Уведомления |

Между базами связь только по ID, общих таблиц нет.

## Главные правила

- Бронирует только Организатор, и только после его подтверждения.
- Паспорта и данные карт мы не храним: паспорт нужен только на время бронирования, оплату проводит Booking System.
- Время хранится в UTC, часовой пояс аэропорта отдельно.
- Уведомление сначала сохраняется, потом отправляется push.
